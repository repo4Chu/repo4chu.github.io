eu me sentei no assento mais barato que o dolibarr pode entregar — uma conta interna comum, às vezes com um único direito de módulo ordinário — e perguntei até onde a aplicação deixa você andar. a resposta: bem longe. esta auditoria rendeu dez achados confirmados em todas as majors estáveis mantidas e no branch de desenvolvimento, validados com mais de 35 confirmações ao vivo contra instâncias reais.

um achado já é público: CVE-2026-78804, uma sql injection no limite de alerta de estoque por armazém que transforma um direito de edição de catálogo em leitura do banco inteiro. os outros nove estão redigidos e aguardam divulgação privada — esta página cita o componente e a classe deles, e nada além disso. um dos nove foi avaliado como não reportável sob a política do próprio projeto.

[01]

como a auditoria foi

escopo · método · confirmações

escopo

o dolibarr/erp é um erp/crm em php com um backoffice muito grande: catálogo, estoque, pedidos, faturas, notas de despesa, rh, documentos, um portal do cliente, uma api rest e um conjunto crescente de módulos mais novos. o alvo era o backoffice de um ponto de observação de baixo privilégio — não a superfície anônima, e nem o painel de admin. a política do vendor cobre as últimas cinco majors estáveis mais o branch de desenvolvimento, então a matriz da auditoria foi 19.0, 20.0, 21.0, 22.0, 23.0 e develop (24.0).

método

  • cada major estável rodou como instância própria a partir das imagens oficiais, com o hardening recomendado pelo vendor ligado (flag de produção, intenção de https forçado, modo estrito de token csrf, sem ferramentas de debug ou builder) — então nada aqui depende de uma instalação desleixada.
  • o teste foi manual e autenticado: ler o caminho de código e depois dirigi-lo como um usuário restrito, com um sufixo de user-agent de teste para que operadores reconheçam o tráfego.
  • cada candidato foi reverificado por versão. um achado só entrou na lista se foi reproduzido ao vivo, não apenas inferido do código-fonte.

confirmações

sete achados reproduziram nas cinco majors estáveis mantidas — só isso já são 35 confirmações ao vivo — e os dois achados limitados por versão foram confirmados onde o código deles realmente existe: um introduzido no 23.0, outro presente só no branch de desenvolvimento. tudo na tabela abaixo é, portanto, evidência, não teoria. os dez que entraram na lista são os que sobreviveram ao triage; uma cauda longa de variantes de controle de acesso colapsou em um punhado de causas-raiz compartilhadas, e essa é a história real deste codebase.

o achado público — CVE-2026-78804

sql injection · limite de alerta de estoque

a aba estoque de um produto permite definir um limite de alerta por armazém. o valor desse limite é lido da requisição como string crua e depois concatenado direto num UPDATE — numa posição numérica sem aspas, sem cast e sem binding de parâmetro. o filtro de input padrão do framework remove html e caracteres de caminho, mas não faz nada contra metacaracteres sql, então o filtro que parece sanitização não é. como o ponto de injeção fica entre aspas, o atacante controla uma expressão sql completa dentro do statement, o que torna possíveis subqueries arbitrárias — e, com elas, extração cega baseada em tempo. o caminho de insert do mesmo registro repete o padrão.

o direito necessário para chegar lá é product → create (ou o seu gêmeo de serviço) — um direito comum de gerente de catálogo que ninguém trata como perigoso.

[04]

impacto

e o teto honesto
  • $leitura arbitrária do banco inteiro, cega, a partir de um direito de editar catálogo
  • $hashes de senha, chaves de api, segredos de configuração, os dados de todos os módulos→ c:h
  • $takeover condicional de conta via uma chave de api de administrador ou hash extraída

o teto importa tanto quanto o alcance. a injeção fica no valor de um UPDATE e o dolibarr emite statements únicos via mysqli, então não há queries empilhadas; a conta padrão do banco não tem privilégio FILE e secure_file_priv é null, então leitura/escrita de arquivo e truques com udf ficam fora da mesa. nenhuma leitura direta de arquivo, nenhum rce direto pelo motor sql. a escalação só é alcançável pela aplicação e só condicionalmente — por exemplo puxando uma chave de api de administrador, se existir, e usando a api rest com ela. o rótulo honesto é comprometimento total da confidencialidade do banco mais takeover potencial de conta.

afetado: 19.0 até 24.0 — reproduzido ao vivo em 19.0.4, 20.0.4, 21.0.4, 22.0.5, 23.0.3 e no develop atual. os interruptores de hardening do vendor não o atrasam: a requisição é um post autenticado normal carregando um token csrf válido.

remediação

para devs + admins

se você mantém o código

  • faça cast do limite (e dos campos numéricos irmãos no mesmo statement) antes de usar: (float) price2num(GETPOST(...)) ou um (int) explícito.
  • prefira prepared statements / parâmetros vinculados para todo valor dinâmico dessa classe — tanto no caminho de update quanto no de insert.
  • o campo pode chegar como um array chaveado por armazém: valide o tipo de cada elemento, não só do primeiro nível.
  • varra o codebase em busca do mesmo padrão de construção; posições numéricas sem aspas são uma classe, não um bug.

se você opera dolibarr hoje

  • conceda product/service → create só a quem realmente cria itens de catálogo; audite quem o detém.
  • rotacione chaves de api e revise contas privilegiadas depois de aplicar o patch — uma leitura do banco pode já ter acontecido em silêncio, e a extração cega não deixa pegada de payload nos dados armazenados.
  • observe anomalias de tempo de resposta na página de estoque de um produto isolado; é o único sinal que esse bug deixa.
[07]

cadeias, em alto nível

conceitual — sem detalhes

individualmente os achados são modestos; compostos, não. mantido deliberadamente conceitual — as peças individuais são descritas só pela classe, e as retidas continuam retidas.

  • um direito comum → as chaves do reino. um direito de editar catálogo compra uma leitura do banco (a sql injection pública); o que você faz com essa leitura — uma chave de api aqui, um hash ali — decide se para nos dados ou sobe até um administrador.
  • um direito de editar conteúdo → execução de código. uma permissão feita para conteúdo de página pode ser empurrada através de uma fronteira de permissão de código que nunca deveria cruzar, e o resultado fica alcançável para qualquer um que depois consiga carregar a página.
  • uma permissão de autoatendimento → um trampolim. o direito de ajustar as próprias permissões vira a concessão de praticamente qualquer direito não administrativo, o que te devolve a uma das duas cadeias acima. a flag de admin em si continua protegida — o teto é alcançado pelas cadeias, não diretamente.
  • zero permissões ainda dói. uma conta novinha sem direito nenhum já alcança dados bancários de folha de pagamento, o repositório de documentos e ações que afetam as finanças — fraude e exfiltração em massa sem nenhum passo de escalação de privilégio.

leitura defensiva: conserte primeiro os dois caminhos baratos de "um direito → tudo", depois o trio de zero permissões, e por fim os padrões de controle de acesso compartilhados por trás do resto — as mesmas duas ou três causas-raiz cobrem a maior parte da lista.

status da divulgação

o que saiu, o que espera
  • janela da auditoriadez achados confirmados validados ao vivo no 19.0–23.0 e no develop; evidência por versão guardada para cada relatório.
  • 2026-09-10CVE-2026-78804 publicado a sql injection do limite de estoque foi a público com uma ferramenta de poc no github.
  • agoraoito achados redigidos cada um está sendo escrito como relatório privado próprio — o projeto rejeita relatórios combinados — e cada um será revalidado contra o branch de desenvolvimento atual antes do envio. os detalhes aqui ficam retidos até as correções saírem.
  • agoraum achado fora do reporting o F-06 (injeção de filtro ldap no login) só existe quando a instância é configurada para autenticação ldap, e o impacto demonstrado cai dentro da zona de exclusão da política — avaliado como não reportável. ele será oferecido ao upstream como um patch de hardening.

posição, para constar: o dolibarr é um projeto voluntário — sem bounty, só crédito, e espera-se que os relatórios sejam escritos por um humano. tudo bem. o objetivo são as correções, e os oito retidos permanecem privados exatamente até os mantenedores terem tido uma chance justa com eles.
