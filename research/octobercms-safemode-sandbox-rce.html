october cms — safe-mode twig sandbox escape → rce · a bypass of the cve-2026-22692 fix

  • vendor=octobercms
  • product=< 4.2.25
  • --cwe=94
  • id=ghsa-8rgj-g632-3qfp

october's cms.safe_mode has one job: let semi-trusted backend users edit template markup without ever running server-side php. the proxy that enforces it, SafeCollection, strips callables from collection method arguments — but only at the top level. laravel's Collection::sortBy() happily accepts an array of comparisons, so a callable hidden as [[['Class','method']]] sails past the filter and gets invoked with two attacker-controlled strings. point it at File::put() and you have an arbitrary file write; and since checkSafeMode() only runs at save time, a .htm written straight to disk with a php code section is never inspected — request it and it runs. safe-mode off, rce as www-data, from an ordinary content-editor account. it's a bypass of the cve-2026-22692 fix; the vendor tracked it as ghsa-8rgj-g632-3qfp and shipped the fix in 4.2.25.


[01]

the bug

a callable one level too deep

safe mode has two jobs: block the php code section of cms templates, and render the remaining twig through a sandbox, System\Twig\SecurityPolicy. the policy is permissive everywhere except method calls — it allow-lists every method on a handful of framework classes, Illuminate\Support\Collection among them. to keep the obvious collection.map('system') from working, october casts the receiver of each method call to a safe proxy: a Collection becomes a SafeCollection that nulls callable arguments. and collect() stays available in safe mode, so an attacker can build a SafeCollection whose items they fully control. that proxy is the whole wall.

the guard walks each argument and nulls anything is_callable() flags — applied to the argument as a whole, never recursing into arrays. a direct map('system') is correctly killed. but is_callable([[['Class','method']]]) is false: the outer value is a one-element array, not a [target, method] pair. a callable buried one level deeper is never stripped.

laravel, meanwhile, ships a method that will call one. sortBy() accepts an array of comparisons; an array that isn't itself callable routes to sortByMany(), whose comparator invokes whatever sits at $comparison[0] when it's a non-string callable — with two collection items as arguments.

why the cve-2026-22692 fix didn't cover this

the blocklist stopped at mapInto

cve-2026-22692 (ghsa-m5qg-jc75-4jp6) was fixed by adding SafeCollection and putting mapInto on its blocklist (v3.7.13 / v4.1.5). for top-level arguments that fix works fine — verified: the naive callable gets nulled and the call dies with a type error. the gap is that any collection method accepting arrays containing callables puts the primitive right back. sortBy/sortByDesc, through sortByMany, are the ones used here; the general audit is "every method that Arr::wrap()s an argument and then treats element 0 as a callable". patching the method list is whack-a-mole by construction.

there's a second gap in the same spirit: the safe cast only wraps three receiver types — Collection, Session\Store and Request. other allow-listed classes that hand a callable to an inner collection aren't wrapped at all; AbstractPaginator::through() and ComponentAttributeBag::filter() both look like the same bug waiting in a different room.

the pieces are older than the advisory window, too. SafeCollection, with its top-level-only filter, has been in october/rain since v3.5.0 and has never blocked sortBy; the collect() helper and the receiver cast the chain relies on landed in october/october at v4.0.0; and at v4.2.21 the class moved to System\Twig\SecurityPolicy\SafeCollection. the published advisory scopes it as ≥ 4.2.0, < 4.2.25, and that's the range to patch against. confirmed dynamically on 4.2.24, the latest release at report time.

poc

4.2.24 · safe_mode=true · trimmed

target: a clean october cms 4.2.24 install with cms.safe_mode = true. starting point: an authenticated low-privilege content editor — editor.cms_pages only, no php/developer permission, no superuser. every request goes through burp; the chain below is trimmed, and no credentials are published here. run things like this only against an install you own.

step 1 — sign in as the content editor through the backend form (csrf and all). an ordinary account an operator would hand to any content person.

step 2 — save a cms page through the backend editor api, sending only markup. twig is allowed in safe mode; the php code section is the only thing the save-time check inspects, and there isn't one. the markup is the dropper: it uses the escape with the File::put gadget to plant a second page that does carry a php code section.

step 3 — render the dropper. the sandbox escape calls File::put() and the webshell page lands on disk.

step 4 — the dropped page's php code section was written, not saved, so no model ever ran checkSafeMode() on it. requesting it executes.

the contrast that proves the sandbox was genuinely active, not accidentally off: the naive collect(['x']).map('system') is correctly blocked — the callable gets nulled — and env()/config() are pulled from twig in safe mode. only the nested sortBy form slips through.

impact

editor.cms_pages → www-data
  • $remote code execution as the web user→ arbitrary php as www-data, from a content-editor session
  • $the safe-mode promise, void→ "templates can't run server code" is the control's entire job; one expression undoes it
  • $privilege escalation→ markup editing (editor.cms_pages) to os-level access, no php/developer or superuser rights held
  • $full compromise from there→ arbitrary file read/write, the database, .env (APP_KEY, db credentials), all tenant content

gadget generality: File::put is just the gadget used here — any (string, string) method that does something useful (a writer, a mailer, a query runner) works the same, so a patch limited to File::put would have been theatre. october's 4.2.25 fix strips callables recursively instead, which is the right shape. same sandbox, third escape: cve-2023-44382, cve-2026-22692 — whose fix this bypasses — and now ghsa-8rgj-g632-3qfp. that pattern points at the allow-list-then-subtract design, not at any single method. distinct from cve-2026-26274 (the db-write safe-mode bypass) and the twig-core cve-2026-24425 (the |sort/|filter/|map/|reduce filters under a SourcePolicyInterface); this one rides the .sortBy() method. october rates it low — safe mode is opt-in, and where it's off a markup editor can run php by design. fair. but for installs that switched safe mode on precisely to contain editors, the control fails all the way to code execution; scored here as cvss 3.1 8.8 (AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H). the label was never the interesting part.

remediation

4.2.25 closes it

if you run october cms

  • upgrade to 4.2.25 or later. the recursive callable strip in SafeCollection is the actual fix — nothing short of it closes this.
  • treat cms template-editing permissions (editor.cms_pages and siblings) as developer-level trust, safe mode on or not. don't hand them to users you wouldn't hand a shell.
  • hunt: templates containing sortBy( with nested arrays, unexpected new .htm files in theme directories, writes outside the theme tree.

if you maintain a sandbox

  • strip callables recursively, or reject any argument containing a callable at any depth. a top-level check is a suggestion, not a filter.
  • explicitly neutralize the array-of-comparisons forms (sortBy / sortByDesc via sortByMany).
  • treat the allow-list as deny-by-default: wrap or refuse every allow-listed class that can hand a callable to an inner collection — AbstractPaginator::through() and ComponentAttributeBag::filter() are the same gap one room over.
  • enforce safe mode at render time in CodeParser too: refuse to compile a non-empty php code section while it's on, so a stray on-disk .htm can't execute on its own, independent of any sandbox bug.
