dolibarr erp 19.0–24.0 — ten findings, one codebase tour

i sat down in the cheapest seat dolibarr can hand out — a plain internal account, sometimes with a single ordinary module right — and asked how far the application lets you walk. the answer: a long way. this audit landed ten confirmed findings across every maintained stable major and the development branch, validated with 35+ live confirmations against real instances.

one finding is already public: CVE-2026-78804, a sql injection in the per-warehouse stock alert threshold that turns a catalog-edit right into a read of the whole database. the other nine are drafted and wait on private disclosure — this page names their component and class, and nothing more. one of the nine was assessed as not reportable under the project's own policy.

[01]

how the audit went

scope · method · confirmations

scope

dolibarr/erp is a php erp/crm with a very large backoffice: catalog, stock, orders, invoices, expense reports, hr, documents, a customer portal, a rest api, and a growing set of newer modules. the target was the backoffice from a low-privilege vantage point — not the anonymous surface, and not the admin panel. the vendor's policy covers the last five stable majors plus the development branch, so the audit matrix was 19.0, 20.0, 21.0, 22.0, 23.0 and develop (24.0).

method

  • each stable major ran as its own instance from the official images, with the vendor's recommended hardening switched on (production flag, forced https intent, strict csrf token mode, no debug or builder tools) — so nothing here depends on a sloppy install.
  • testing was manual and authenticated: read the code path, then drive it as a restricted user, with a test-user-agent suffix so operators can recognise the traffic.
  • every candidate was re-checked per version. a finding only made the list if it was reproduced live, not just inferred from source.

confirmations

seven findings reproduced on all five maintained stables — that's 35 live confirmations on its own — and both version-gated findings were confirmed where their code actually exists: one introduced in 23.0, one present only on the development branch. everything in the table below is therefore evidence, not theory. the ten that made the list are the ones that survived triage; a long tail of access-control variants collapsed into a handful of shared root causes, which is the real story of this codebase.

the public one — CVE-2026-78804

sql injection · stock alert threshold

the stock tab of a product lets you set a per-warehouse alert threshold. the value for that threshold is read out of the request as a raw string and later concatenated straight into an UPDATE — in an unquoted numeric position, with no cast and no parameter binding. the framework's default input filter strips html and path characters, but it does nothing against sql metacharacters, so the filter that feels like sanitization isn't. because the injection point sits between quotes, an attacker controls a complete sql expression inside the statement, which makes arbitrary subqueries — and therefore blind, time-based extraction — possible. the insert path for the same record repeats the pattern.

the right required to reach it is product → create (or its service twin) — an ordinary catalog-manager right that nobody treats as dangerous.

[04]

impact

and its honest ceiling
  • $arbitrary read of the entire database, blind, from a catalog-edit right
  • $password hashes, api keys, configuration secrets, every module's data→ c:h
  • $conditional account takeover via an extracted administrator api key or hash

the ceiling matters as much as the reach. the injection sits in the value of an UPDATE and dolibarr issues single statements through mysqli, so there are no stacked queries; the default database account has no FILE privilege and secure_file_priv is null, so file read/write and udf tricks are off the table. no direct file read, no direct rce through the sql engine. escalation is reachable only through the application and only conditionally — for example pulling an administrator's api key, if one exists, and using the rest api with it. the honest label is full database confidentiality compromise plus potential account takeover.

affected: 19.0 through 24.0 — reproduced live on 19.0.4, 20.0.4, 21.0.4, 22.0.5, 23.0.3 and current develop. the vendor's hardening switches do not slow it down: the request is a normal authenticated post carrying a valid csrf token.

remediation

for devs + admins

if you maintain the code

  • cast the threshold (and the sibling numeric fields in the same statement) before use: (float) price2num(GETPOST(...)) or an explicit (int).
  • prefer prepared statements / bound parameters for every dynamic value in that class — both the update and the insert path.
  • the field can arrive as an array keyed per warehouse: type-check each element, not just the first level.
  • sweep for the same build pattern elsewhere in the codebase; unquoted numeric positions are a class, not a bug.

if you run dolibarr today

  • grant product/service → create only to people who genuinely create catalog items; audit who holds it.
  • rotate api keys and review privileged accounts after patching — a database read may have already happened silently, and blind extraction leaves no payload footprint in stored data.
  • watch response-time anomalies on the stock page of a single product; it's the only signal this bug leaves behind.
[07]

chains, at a high level

conceptual — no detail

individually the findings are modest; composed they aren't. kept deliberately conceptual — the individual pieces are described by their class only, and the withheld ones stay withheld.

  • one ordinary right → the keys to the kingdom. a catalog-edit right buys a database read (the public sql injection); what you do with that read — an api key here, a hash there — decides whether it stops at data or climbs to an administrator.
  • one content-edit right → code execution. a permission meant for page content can be pushed across a code-permission boundary it was never supposed to cross, and the result is reachable by anyone who can then load the page.
  • a self-service permission → a bootstrap. the right to adjust your own permissions becomes a grant of practically any non-administrative right, which lands you back at either of the two chains above. the admin flag itself stays protected — the ceiling is reached through the chains, not directly.
  • zero permissions still hurts. a brand-new account with no rights at all already reaches payroll bank details, the document store, and finance-affecting actions — fraud and mass exfiltration without any privilege-escalation step.

defensive reading: fix the two low-cost "one right → everything" paths first, then the zero-permission trio, then the shared access-control patterns behind the rest — the same two or three root causes cover most of the list.

disclosure status

what's out, what waits
  • audit windowten findings confirmed validated live across 19.0–23.0 and develop; per-version evidence kept for every report.
  • 2026-09-10CVE-2026-78804 published the stock threshold sql injection went public with a poc tool on github.
  • noweight findings drafted each is being written up as its own private report — the project rejects combined reports — and each will be re-validated against the current development branch before filing. details here stay withheld until fixes ship.
  • nowone finding retired from reporting F-06 (ldap filter injection at login) only exists when an instance is configured for ldap authentication, and its demonstrated impact falls inside the policy's exclusion zone — assessed as not reportable. it will be offered upstream as a hardening patch instead.

stance, for the record: dolibarr is a volunteer project — no bounty, credit only, and reports are expected to be written by a human. that's fine. the goal is fixes, and the withheld eight stay private exactly until the maintainers have had a fair shot at them.
